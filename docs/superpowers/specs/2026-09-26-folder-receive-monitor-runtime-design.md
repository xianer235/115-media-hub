# 文件夹接收与文件夹监控：设计运行逻辑与运行记录展示

日期：2026-09-26
状态：已实施（对应 `0.12.0`，未发布）
范围：接收夹整理与文件夹监控的触发、执行、结算口径，以及运行记录列表与详情展示。

与历史文档的关系：

- `2026-09-23-folder-monitor-workflow-design.md`：更大范围的工作流讨论稿（含未实施设想）。
- `2026-09-23-folder-monitor-log-redesign.md`：上一轮界面整改方案。
- 本文：当前权威口径，记录「接收夹只做到识别与整理移动、STRM 生成独立成文件夹监控任务」之后的实际行为。文档与代码冲突时以代码为准。

## 1. 术语

| 概念 | 含义 |
| --- | --- |
| 任务配置 | `monitor_tasks` 里的一条任务：扫描任务的目录 / 输出 / 策略，或接收夹任务的中转目录与分发目标。 |
| 触发请求 | 一次用户或系统发起的刷新意图（手动、定时、推送、导入完成、接收夹分发、系统补扫等）。 |
| 一次运行 | 一条 `monitor_runs` 记录，`run_kind` 为 `scan`（目录同步）、`change`（变更同步）或 `inbox`（接收夹整理）。 |
| 工作单元 | 运行记录列表里的一行：新数据里每条运行都独立成行，不再折叠父子。 |
| 独立目录同步任务 | 接收夹分发一个条目后触发的 `scan` 运行，`source=inbox_dispatch`，无父运行、无下游链接。 |

## 2. 接收夹整理（`run_kind=inbox`）

### 2.1 两步链路

1. **识别**：读取接收夹，识别每个条目的影视信息（规则匹配 + AI 兜底，低置信度不采纳）。
2. **整理移动**：按目标监控任务的刮削规则在网盘内重命名 / 整理，再按电影 / 电视剧分发到对应监控目录；目标已有同名媒体文件夹时合并进去。

STRM 生成**不属于**接收夹记录：每条分发成功的条目会立刻排一条独立的目录同步任务（来源「接收夹分发」），由它扫描目标目录并生成 / 更新本地播放文件。

### 2.2 触发来源

| 来源 | 入口 |
| --- | --- |
| 手动 | 面板「立即整理」、`/monitor/start`、`/scraper/quick-import/run` |
| 定时 | 接收夹任务的 `cron_minutes` |
| 离线下载完成 | 115 离线 watcher 完成后 `notify_quick_import("offline")` |
| 导入完成 | 资源导入 / 转存完成后的 `notify_quick_import("import")` |

触发采用非阻塞登记：整理正在执行时只记录「还需再跑一轮」，本轮结束后由工作线程自动续跑一轮全量整理，直到接收夹稳定。

### 2.3 定稿口径

- 分发完成即定稿，不进入 waiting、不等待任何下游：
  - 有分发且无留守 → 已完成；有分发但有留守 → 部分完成；
  - 没有可整理内容 → 无变化；配置 / 识别失败 → 失败；用户中断 → 已中断（已完成的远端操作不回滚）。
- 判定只认「移动是否提交」：搬运后的接收夹空目录清理失败先收集，本轮搬运结束再统一重试一次；清掉的只记过程事件「接收夹空目录已清理」，确实还残留才写一条「接收夹残留待清理」，不算失败、不算留守；115 删除响应无法识别时用父目录列表复核（条目已不在即视为已清掉）。
- 整理残留的空壳目录（整棵子树没有文件）在整理时直接清理，不再被反复识别与留守。
- 结果字段只保留 `moved`、`left` 与留守明细；**不再写** `children` / `waiting_children`。
- 留守原因（未识别、低置信度、重名冲突、整理失败、搬运失败、已中断）逐条写进问题事件，「留在接收夹」条目在问题页签可查。
- 分发事件明细保留 `child_run_id` 与识别信息（原名 → 识别为、识别来源、置信度），仅作溯源；不建立运行父子关系。

## 3. 文件夹监控

### 3.1 目录同步（`run_kind=scan`）

1. 校验任务、认证、路径与输出地址，按配置等待延时。
2. 从任务根目录或指定目录开始；「目录时间检查」只比较第一层文件夹，相同则沿用已有索引跳过分支。
3. 递归读取需要的分支，按扩展名 / 大小过滤，生成或更新 STRM；内容相同默认不重写（全量重写由写入策略决定）。
4. 开启清理且本轮无目录读取失败时，删除索引内已记录但本次未出现的 STRM；读取失败的分支保留索引并标记待补扫。
5. 更新文件索引与首层时间基线；开启自动整理时对新增媒体调用整理流程，产生的远端变更进入变更事件。

### 3.2 变更同步（`run_kind=change`）

- 处理面板操作 / 刮削产生的持久化变更事件：优先按文件 ID 与已有索引精准更新 STRM，必要时局部核对受影响目录。
- 目录清单未知时标记 `manual_required`；这些目录按目录逐个排队成 **系统补扫**（`source=auto_rescan`，挂在变更同步下并等待），补扫成功后按真实扫描范围清除事件并结算链路。
- **不挂接收夹父运行、不等独立分发任务**：接收夹分发的条目由独立目录同步任务负责，变更同步只按「任务 + `source=inbox_dispatch` + 覆盖范围」去重补排，并记一条 `delegated` 说明事件（`independent_children` 计数）。
- 本次已经用精准路径同步过（生成 / 删除过 STRM）的分发条目**不再补排**目录扫描，避免重复扫描与「无变化」噪音记录。
- 结论口径：只有「需要自己补扫」的目录才计入未完成（部分完成 / 等待补扫）；被独立任务覆盖的目录不再拖累结论。

### 3.3 系统补扫策略

- 每个待补扫目录**只自动尝试一次**：成功即清除提示；失败 / 部分完成后不再自动重排，卡片标红「补扫失败 N」需人工处理。
- 队列失败由监控调度每 15 秒兜底重排（已在排队 / 执行中的跳过）。

## 4. 触发来源总表（监控侧）

| 来源 | 说明 | 运行来源值 |
| --- | --- | --- |
| 手动 | 卡片「运行」、指定目录扫描 | `manual` |
| 定时 | `cron_minutes` 到期 | `cron` |
| Webhook | `/webhook/{任务名}` | `webhook` |
| 资源导入 / 订阅 / 离线完成 | 导入完成后按保存目录触发 | `resource` / `subscription` / `offline` |
| 网盘变更 | 面板操作、刮削、回退产生的变更事件 | `change` |
| 接收夹分发 | 分发条目后的独立目录同步任务 | `inbox_dispatch` |
| 系统补扫 | 变更同步为未知清单目录排队 | `auto_rescan` |
| 重新运行 | 运行记录里的「按原范围重新运行」 | `retry` |

筛选界面按 5 组呈现：手动操作 / 定时执行 / 推送通知 / 导入完成 / 系统跟进。

## 5. 状态与结算

| 状态 | 含义 |
| --- | --- |
| `queued` / `running` | 排队中 / 执行中 |
| `waiting` | 变更同步等待自己的自动补扫（历史上接收夹也用过；新数据不再产生接收夹 waiting） |
| `completed` / `no_change` | 已完成 / 完成检查但无变化 |
| `partial` | 部分完成：读取失败、仍有留守、需人工处理的补扫 |
| `failed` | 必要步骤失败 |
| `cancelled` | 已取消 / 已中断（执行过的操作保留） |

结算规则：

- 接收夹分发完成即终态；`settle_run_chain` 只服务变更同步与自动补扫这类真实等待链。
- 历史 waiting / 父子记录由启动时的 `reconcile_waiting_runs()` 与 `settle_deferred_runs()` 按证据收敛，不改写新数据。

## 6. 记录模型

| 表 | 职责 |
| --- | --- |
| `monitor_runs` | 一次运行：类型、任务名、来源、范围、对象、状态、结论、结果计数、时间戳。 |
| `monitor_run_events` | 运行事件：`category` ∈ `process` / `remote` / `strm` / `problem`，含 `operation`、`status`、`title`、`detail_json`。 |
| `monitor_run_links` | 运行关系：`child` / `downstream` / `retry_of`（接收夹分发的新数据不再使用前两种）。 |

结果计数（`result_json`）：`moved`、`left`、`generated`、`deleted`、`failed_dirs`、`manual_required`、`dispatched_items`、`waiting_children` 等，按运行类型取用。

## 7. 运行记录展示

### 7.1 列表

- 一行一个工作单元：任务 · 对象、一句结论、类型标签（接收夹整理 / 目录同步 / 变更同步）、状态徽标、查看详情。
- 按**开始时间**排序（未开始退回排队时间），分页游标用同一键；后台状态更新不会让条目跳到列表最前。
- 独立分发任务在列表里自然成行（来源「接收夹分发」），不再折叠进接收夹行。
- **同一次分发的「变更同步 + 独立目录同步」合并成一行**（展示层合并，数据层仍是两条记录）：默认列表要求同任务、范围归一化后一致、入队时间相差不超过 60 秒才配对，主行取目录同步（类型标签 / 状态 / 结论），副行写「上游：变更同步 · 已同步 N 条网盘变更」；目录同步详情在概览下方给出可点击的「上游 · 变更同步」跳转。
- 配对按两个成员里排序更靠后的那个收口分页游标（不跳过、不重复）；分页窗口内只有一条时各自独立成行；按类型 / 来源 / 状态筛选时保持扁平，不做合并。

### 7.2 详情：按任务类型匹配的互斥页签

每个运行只出现与它职责匹配的页签，不适用的页签不渲染；切到不适用的页签一律回到概览。

| 运行类型 | 页签 | 说明 |
| --- | --- | --- |
| 接收夹整理 `inbox` | 概览 / 网盘变更 N / 问题 N | **没有本地文件页签**：接收夹只做识别与整理移动，STRM 由独立任务生成。 |
| 目录同步 `scan` | 概览 / 本地文件 N / 问题 N | **没有网盘变更页签**：目录同步只读网盘、写本地播放文件。 |
| 目录同步（含自动整理） | 概览 / 网盘变更 N / 本地文件 N / 问题 N | 例外：本次确实做了自动整理（网盘操作）时保留网盘页签，行动作显示在「自动整理」一节。 |
| 变更同步 `change` | 概览 / 网盘变更 N / 本地文件 N / 问题 N | 一边是检测到的网盘变更，一边是它带来的本地播放文件增删。 |
| 旧记录（缺 `run_kind`） | 概览 /（有数据才出现网盘、本地）/ 问题 | 按来源推断任务类型；无法判断时只显示有数据的页签。 |

各页签内容：

- **概览**：接收夹运行显示两步进度条「识别 → 整理移动」（✓ / ● / ○ / ✕）；下面是结果卡：类型 + 状态 + 一句结论 + 未完成内容 + 最多 3 个关键数字 + 范围 / 用时 / 触发来源 + 操作按钮。目录同步 / 变更同步不显示步骤条。
- **网盘变更**：逐条列出网盘操作明细——动作、时间，以及**原位置 / 原名称 / 新位置 / 新名称**四行字段（接收夹整理还带识别来源与置信度），目录移动另附删除 / 生成本地文件计数。接收夹分「整理重命名」「移动到监控文件夹」两节，目录同步显示「自动整理」，变更同步单节「网盘变更」。
- **本地文件**：逐条列出本次实际新增 / 删除的本地播放文件，每条同时给出**网盘位置 / 网盘名称**与**本地位置 / 本地名称**（变更同步的文件级事件用 `strm_path` / `remote_path`，旧记录用 `new_path` / `new_remote_path` 兜底）；变更同步的文件夹级变更也会按真实影响的 STRM 逐条记录（单次最多 200 条，超出部分用一条「另有 N 个本地播放文件未逐条列出」兜底，旧数据仍用汇总行）。
- **问题**：问题事件 + 失败的网盘 / 本地文件事件 + 旧记录按结果推导的未完成内容；原始英文错误收进随行可展开的中文诊断块。

- 页签计数取 `get_run_detail` 的 `counts`（整次运行的权威统计），不是已加载条数；切页签只重渲染，不重新请求。
- 每个事件页签显示「已显示 X / 共 N 条」与「加载更多」；运行中的详情每 5 秒静默刷新概览数字与页签计数。
- 历史父子记录仍兼容展示：接收夹概览底部列出旧子任务并可点开。

## 8. 兼容与迁移

- 不新增数据表；`monitor_runs` / `monitor_run_events` 结构不变，新数据只是不再建立接收夹父子链接。
- 已存在的 waiting 接收夹记录与 children 链接保持原样，由启动收敛逻辑与列表历史分组兼容展示。
- 旧文本日志继续作为历史诊断入口，不参与新运行记录的状态推断。
