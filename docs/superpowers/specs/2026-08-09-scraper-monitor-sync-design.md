# 刮削操作驱动的精准 STRM 同步设计

## 背景

刮削管理和文件夹监控原先各自维护状态。用户在刮削页对 115 文件执行重命名、复制、移动、删除或新建文件夹后，监控索引和本地 STRM 不知道远端已经发生变化，只能再次执行一次全量或局部监控扫描才能收敛。对大目录来说，这会产生不必要的 115 列目录请求，也让操作结果和本地媒体库之间出现可见延迟。

本设计把刮削操作的已知路径变化变成持久化事件。正常操作不读取监控根目录；只有快照缺失、远端操作结果未确认或精确处理失败时，才在受影响子树或其父目录内做局部校正。

## 目标与边界

- 115 刮削操作成功后，按旧路径和新路径命中所有覆盖路径的监控任务，并精确更新 STRM 与 `monitor_files`。
- 远端调用前持久化 `prepared` 事件；调用失败、进程中断或启动恢复时转为带校正标记的待处理事件。
- 变更事件通过独立的 `change` 监控队列处理，并与普通扫描串行；变更处理不进入普通扫描 walker。
- 文件夹已建立索引时克隆索引清单；索引未知时只读取新文件夹子树，并受目录数、文件数和重试上限保护。
- 继续遵守扩展名和最小文件大小过滤。显式删除只删除事件明确指向的 STRM，不受 `sync_clean` 影响；`strm_write_mode=full` 不改变精确事件。
- 更新受影响第一层分支的 `monitor_dirs.needs_rescan`，清除失效旧目录状态，交给下一次普通监控定向复核。
- 仅 115 生成事件；夸克、阿里、天翼和 123 等其他网盘保留原文件管理行为，并返回 `not_applicable` 同步状态。

不在本设计中实现原地修改 STRM 内容、迁移非 STRM 元数据、扩大到整个监控根目录的兜底扫描，或新的独立监控页面。

## 组件与数据模型

### 持久化事件

`monitor_change_events` 是独立于 `monitor_files` 和 `monitor_dirs` 的事件表。每一条事件按监控任务拆分，保存：

- `operation`：`create`、`copy`、`move`、`rename`、`delete`；
- `old_path`、`new_path`：115 挂载点下的相对路径；
- `entry_snapshot_json`：条目 ID、名称、父路径、类型、大小和修改时间，以及已知文件夹清单；
- `task_name`、`source_action`、`dedupe_key`：来源和批量动作去重信息；
- `status`：`prepared`、`pending`、`processing`、`completed`、`failed`；
- `needs_reconcile`、`retry_count`、`next_retry_at`、`last_error`；
- 目录/文件处理统计和创建、确认、完成时间。

唯一键是 `dedupe_key + task_name + old_path + new_path`。直接操作使用请求序号；批量刮削使用“任务 ID + 动作 ID + forward/rollback”，因此执行和回退可以安全重放。

### 状态流转

```text
             115 调用成功
prepared --------------------> pending
   |                             |
   | 调用失败/启动恢复            | 处理器领取
   v                             v
pending (needs_reconcile=1) -> processing
                                  |
                         +--------+--------+
                         |                 |
                      completed         failed
                                  (退避重试，保留事件)
```

`prepared` 和 `processing` 在启动时统一转为 `pending + needs_reconcile=1`。重复确认依据数据库中的实际状态返回 `queued`、`reconcile_queued`、`processing`、`completed` 或 `failed`，不会把已完成事件再次报告为排队。

## 事件产生与路径匹配

刮削页的重命名、复制、移动、删除和新建文件夹请求增加可选快照和 `request_id`。缺少快照的旧客户端仍先执行原网盘操作，但返回 `monitor_sync.status=unavailable`，不猜测路径。快照不完整时只创建能够安全定位的事件；无匹配监控任务返回 `not_matched`。

请求中的 `entry_id/entry_ids` 是本次操作的权威条目集合。快照必须携带与请求一致的显式 `id/cid/fid` 才能参与同步，不按数组位置补猜 ID，也不使用混入选择列表的旧条目。重命名快照 ID 不一致、删除或移动快照不属于请求集合时，网盘操作保持兼容，但相应条目不创建同步事件。

准备阶段对旧路径、新路径分别匹配所有覆盖它们的监控任务，去重任务名后为每个任务插入事件。对于文件夹旧路径，先从已有 `monitor_files` 和 `monitor_dirs` 捕获索引清单；该清单随事件快照保存，使跨监控任务移动和已有索引复制无需再次列目录。

批量刮削执行和回退复用同一事件生命周期。批量动作在远端调用前落库，成功后确认，异常时标记局部校正；事件去重键区分正向和回退，避免两次动作互相覆盖。旧、新路径完全相同的动作直接跳过，不创建无意义的监控事件。

## 精确处理器

### 文件

- 删除或移出监控范围：删除对应任务的 `monitor_files` 行；仅当没有其他监控任务继续引用同一个 `local_rel_path` 时才删除物理 `.strm`，全程不读取 115 目录。
- 新增、复制或移入：按新路径和快照元数据生成 STRM，并 `INSERT OR REPLACE` 索引。
- 重命名或移动：先删除旧 STRM/索引，再按新路径生成；不修改原文件内容。
- 扩展名或大小不符合任务过滤时不生成 STRM，但仍完成事件和基线更新。

### 文件夹

- 删除旧路径时以 `monitor_files` 的路径前缀删除索引和 STRM；只操作托管的 `.strm`，字幕、NFO、海报等文件保持不变。
- 已知索引的复制、重命名和移动使用保存的文件清单克隆，不列远端目录。
- 未知目标文件夹先完整收集目标子树，再一次性写入 STRM/索引。目录最多 80 个、文件最多 1200 个；超限或列目录失败时事件进入退避重试，收集阶段不留下半成品文件。
- 精确处理完成后，旧目录状态被删除，旧父级和新路径对应的第一层分支标记 `needs_rescan=1`。监控根目录直属文件使用空路径根基线；顶层文件夹改名仍只标记实际新分支，不制造无意义的空根分支。普通监控下一次只需定向复核这些状态。

### 局部校正

校正只在受影响文件的父目录或目标文件夹子树内读取。快照带显式条目 ID 时只接受相同 ID 的远端条目，不使用同名但不同 ID 的文件兜底；确认到同一 ID 后仍按远端实际名称重建索引。创建或复制事件在目标父目录内找不到目标条目时进入退避失败并保留。直接位于监控根目录的文件不会通过列根目录来兜底；无法在局部边界内确认时保留失败事件，绝不扩展为监控根目录扫描。

## 队列、恢复与保留

监控队列条目带 `mode=scan|change`。同一任务的普通扫描和变更同步不会合并，队列执行器保持全局串行；变更模式只消费持久化事件。队列锁同时保护“dispatcher 已安排、worker 尚未接管”的保留状态，空闲时连续入队只会创建一条调度链；任务不存在或配置错误的早退分支也会释放保留并继续下一任务。启动阶段先恢复未完成事件，再由定时循环把到期失败事件重新入队。失败最多自动重试 5 次，采用 5 秒起的指数退避；达到上限仍保留 `failed` 记录供用户诊断。

`completed` 事件保留 30 天后清理；`pending`、`processing` 和 `failed` 永不自动清理。监控状态接口按任务返回待同步和失败数量，任务卡显示数量，变更处理日志记录完成、失败、生成、删除及局部读取统计。

## 接口状态

成功的刮削操作响应保留原字段并增加：

```json
{
  "monitor_sync": {
    "status": "queued",
    "matched_tasks": ["影视监控"],
    "event_count": 1,
    "event_ids": [42]
  }
}
```

状态可能是 `not_applicable`、`unavailable`、`not_matched`、`reconcile_queued`、`processing`、`completed` 或 `failed`。前端沿用现有提示和任务卡，不增加独立页面。
