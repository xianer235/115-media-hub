# TG 单文件 ED2K 消息支持设计

## 背景与根因

资源通用链接解析器 `extract_resource_links()` 已支持 ED2K，现有 ED2K 导入弹窗和 115 离线任务也能处理单个文件链接。但 TG 频道页面解析器单独维护了一套正文链接提取规则，只识别 magnet 和 HTTP(S)，导致直接写在频道消息正文里的单文件 `ed2k://` 链接在入库前丢失，最终成为 `link_type=unknown`。

## 目标

- TG 频道消息直接包含一个合法 ED2K 文件链接时，将资源识别为 `link_type=ed2k`。
- 沿用现有 ED2K 导入弹窗：默认选中唯一文件，并允许新建文件夹后保存到 115。
- 保持一条 TG 消息只选择一个主资源链接的现有行为，不改变多链接优先级和资源入库数量。

## 实现设计

`parse_telegram_posts_page()` 不再用本地 magnet/HTTP 正则拼接正文候选，而是把消息正文和已提取的链接属性交给公共 `extract_resource_links()`。解析结果继续经过现有 Telegram 内部链接过滤、去重和 `choose_resource_link()` 主链接选择。

这样 TG 页面解析与手工文本导入共用同一套协议识别规则。以后公共解析器增加新的资源链接类型时，TG 正文解析不需要再次单独补协议分支。

数据流保持为：TG HTML -> 提取消息正文和链接属性 -> 公共资源链接提取 -> 过滤 Telegram 内部链接 -> 选择主链接 -> 生成现有资源项。后续前端候选判断、单文件 ED2K 解析和批量任务接口均保持不变。

## 错误与兼容行为

- 格式非法、缺少文件大小或哈希不合法的 ED2K 文本不会被公共正则识别，沿用当前未知资源行为。
- 现有 magnet、HTTP(S) 和网盘分享链接识别与优先级保持不变。
- 不修改 ED2K 弹窗、保存接口、离线任务结构或数据库结构。

## 测试与验证

- 先用用户提供的完整电影消息增加 TG 页面解析回归测试，确认当前实现无法得到 ED2K 链接。
- 修复后断言 `link_url` 保留完整 ED2K、`link_type` 为 `ed2k`，并确认资源标题仍来自电影消息而不是文件名。
- 复跑 ED2K、TG 资源相关测试和完整 unittest。
- 运行项目 `compileall` 与 `git diff --check`。本次不修改前端，因此不需要新增浏览器交互验证。

## 非目标

- 不把一条 TG 消息拆成多个资源项。
- 不调整多种链接并存时的主链接优先级。
- 不改变单文件 ED2K 的文件夹默认值或保存交互。
