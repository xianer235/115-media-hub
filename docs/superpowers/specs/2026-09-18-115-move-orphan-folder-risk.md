# 115 网盘批量移动导致文件夹“孤儿/不可见”的风险备忘（2026-09-18）

> 状态：平台行为知识 + 本项目代码风险评估，**暂不实施修复**。
> 触发背景：一次线上事故并非 115-media-hub 直接造成，而是用户自研的另一个项目批量搬移 115 文件后，
> 目标目录在官方列表里“消失”、只能搜索找到。此处把平台行为、排查结论与我们对自身代码的同类风险固化下来，
> 供后续开发在做 115 移动/删除相关功能时对照。

## 一、现象

- 文件在 115 官方网页/客户端的普通目录树里“看不到”，但全局搜索仍能找到、能打开、能播放、仍占用空间。
- 搜索返回的位置不准确，常被用户描述成“跑到网盘根目录下面”。
- 从项目日志看，文件是被成功“移动”到了目标目录，接口也返回成功，但用户侧就是走不到那个目录。

## 二、根因（115 平台侧）

115 的 `files/move` 在批量移动（尤其从/向系统目录「我的接收 / 最近接收 / 离线下载 / 礼包文件」搬）后，
可能让目标文件夹进入“孤儿”状态：

- 文件夹的 `pid`（父目录 id）指向某个父目录；
- 但该父目录的正常 `files` 列表里已经不再包含这个文件夹。

结果是：普通目录树按 `files?cid=<pid>` 拉列表时拉不到它，因此前端“走不到”；但该文件夹和内容仍真实存在，
所以搜索、播放、占用空间都正常。这是 115 目录元数据/索引不同步的已知 bug，不是文件被删除。

官方社区同款反馈（外部链接，仅供参考）：

- “我的接收文件夹不见了，里面文件跑到根目录下面不显示怎么办？”（115 论坛新版页面反馈帖跟帖）。
- “115 有时移动文件并没有真实移动，文件虽然看着移到了指定目录，但在原目录还可以搜到。”
- “我的接收”目录删除后正常列表进不去，只在移动操作里能看到。

## 三、本次只读排查记录

使用用户导出的 115 Cookie，仅做只读探测（列目录、搜索、解析路径），未做任何写操作。关键证据：

- 「最近接收」是根目录下真实文件夹，cid `3507237712929228576`，内含 466 项个人影视文件。
- 搜索「速度与激情」可命中全系列，已整理成 `速度与激情N 4K REMUX（年份）`，真实位于：
  `4K REMUX（774部）40TB / 速度与激情N 4K REMUX（年份）`。
- `4K REMUX（774部）40TB` 的 cid = `3484304924869658557`，其 `pid = 3477229463886890118`。
- 用 `files?cid=3477229463886890118` 列目录，返回的是与根目录完全相同的 29 个文件夹，但**不含**
  `4K REMUX（774部）40TB`；对 `3477229463886890118` 做 `medialist` 解析返回 `state=False`。

即：`4K REMUX（774部）40TB` 的父指针指向的位置，正常列表里却列不出它——典型“孤儿”状态。

## 四、恢复方法

- 文件未删：用官方搜索定位 → “打开所在目录”直接进入孤儿文件夹 → 把文件移动到可见目录，
  必要时再移回以触发 115 刷新索引。
- 不要清空回收站、不要使用 115 的“文件排重 / 清理”功能。

## 五、对本项目（115-media-hub）代码的风险评估

结论：**存在同源风险**，因为我们同样直接调用 115 `files/move`，且接收夹整理也是“批量搬移”。具体缺口：

1. **未拦截 115 系统目录当接收夹/目标**：`validate_quick_import_config`
   （`app/services/quick_import.py:151`）只校验任务/启用/路径/目标/路径重叠，不检查是否为
   「我的接收 / 最近接收」这类系统目录；`resolve_115_folder_id_by_path`
   （`app/providers/pan115.py:1308`）把这类目录当普通文件夹按名解析。用户若把接收夹设成“最近接收”，
   我们就会照搬，存在踩中同款 115 bug 的可能。

2. **搬完未回验就删源**：`_dispatch_organized_entry`（`app/services/quick_import.py:533`）与
   `_merge_organized_folder_into_existing`（`app/services/quick_import.py:459`）都是
   “先 `move_scraper_entries` 再 `delete_scraper_entries`”；`move_115_entries`
   （`app/providers/pan115.py:1093`）只判断接口返回的 `state/errno`，没有再去目标目录确认该条目确实出现。
   若遇到“move 返回成功但未真实移动”的边界情况，后续删源会把文件误移进回收站。

3. **缺 source→target 审计**：`run_quick_import`（`app/services/quick_import.py:609`）里 `moved` 只记录
   `{name, target, task_name, job_id}`，没有来源 cid/路径与目标 cid/路径，出事后难精确回滚追查。

**相对安全的一点**：我们的删除走 `delete_115_entries`（`app/providers/pan115.py:1232`）→ `rb/delete` 回收站，
不是硬删，误删可恢复；且只搬高置信度媒体、只限定在配置的接收夹内。

## 六、后续开发准则

- 所有 115 `move` 都假设“可能未真正生效”：搬完后在目标目录列表里回验条目确实存在，再继续或删源。
- 批量移动要有“搬前清单 + 确认”（自动触发也要落审计），并记录 source cid/路径 → target cid/路径。
- 不要把 115 系统目录（我的接收 / 最近接收 / 离线下载 / 礼包文件）当普通文件夹处理；
  能按名拦截就拦截，拦截不了也要强提示。
- 删除类操作优先走回收站，并保留可回滚记录。
